## Правила оценивания

Сначала оценивается правильность каждой версии, затем применяется коэффициент срока. За задачу выбирается максимальный итог из доступной истории; при равенстве — более правильная, затем более ранняя версия. Поздний перенос и переименование не отменяют ранний зачёт. Части разных версий не склеиваются, несколько решений одной задачи не суммируются. Время — Git committer date, переведённое в МСК (UTC+3); оно не доказывает точное время фактического push. Новые коммиты с отчётами не считаются исходными сдачами.

Максимумы взяты из условий; частичный зачёт за правильность — принятая при проверке методика. Обычно 0.75 максимума за локальную ошибку в правильном алгоритме, 0.5 за существенное выполнение части требований, 0.25 за содержательную попытку с несколькими существенными ошибками, 0 за пустой файл/отсутствие ответа. Процент успешных тестов не является формулой оценки. Успешные тесты не отменяют обнаруженную при чтении ошибку памяти или нарушение явного ограничения.

Не снижается балл за имя файла, изменённую нумерацию или объединение независимых задач в одном файле. Самостоятельные фрагменты в общем файле могут быть оформлены комментариями; они оцениваются по содержанию и при необходимости извлекаются только в проверочную копию. Задачи с письменным ответом не требуют компилируемого демонстрационного main. Если в задании просят конкретный фрагмент — например цикл обнуления — оценивается этот фрагмент для исходных данных условия; ошибочное дополнительное окружение отмечается отдельно. Явно предложенный правильный альтернативный фрагмент в комментарии также принимается.

Подписи, лишние пробелы, отладочная печать и разбиение числовой последовательности на строки не штрафуются, если требуемые значения однозначно читаются в нужном порядке. Склеивание соседних чисел без разделителей и лишние клетки шахматной доски считаются ошибкой вывода. Не вводится запрет второго массива там, где его нет в условиях. Сами решения студентов не исправляются; в ветки добавляются только README.

1.1: по 1/14 максимума за правильную классификацию. При `int x,*p,**q` допустимы **а,в,г,и,л,м,о**: `*p`, `p=&x`, `&p`, `q=&p`, `*q`, `**q`, `&*p`. Остальные недопустимы по типам/ограничениям операций. Здесь оцениваются типы; выполнение разыменования неинициализированного указателя не разрешается.

1.2: правильный письменный ответ — **одинаковый адрес a дважды и число 3**. p и q указывают на один объект, `(*q)++` меняет a с 2 на 3. Нужен именно ответ; повтор исходной программы без предсказания вывода сам по себе не засчитывается. Проверяющий не запускал этот фрагмент для получения ответа.

1.3: обмен через `*a_ptr`/`*b_ptr` и временную переменную; доступ к a,b в самом обмене должен идти через указатели. 1.4: на обычной четырёхбайтовой little-endian платформе байты печатаются от старшего к младшему как в примере `00 00 04 01`; приняты оба регистра hex. Зависимость от размера int/порядка байтов отмечается рекомендацией, поскольку переносимость на произвольную архитектуру отдельно не требовалась.

Для массивов используются 0≤N<100, для вставки 0≤k≤N; проверяется N=99, когда после вставки элементов становится 100. В поиске при повторах принят любой правильный индекс, поскольку выбор первого в условии не задан. Суммы тестируются в представимом диапазоне int, произвольная точность не требуется.
