# C · конспекты семинаров

Статическая платформа для конспектов по программированию на C. Преподаватель редактирует обычный Markdown в Obsidian, отправляет изменения в `main`, и GitHub Actions публикует сайт на GitHub Pages. Backend, база данных и внешние сервисы компиляции не нужны.

В комплекте 3 семинара, 8 тем и 7 заданий: ввод/вывод, типы данных, условия, циклы, массивы, строки, указатели и динамическая память. Все блоки `c` становятся редакторами CodeMirror 6. Изменённая программа действительно компилируется Clang 18.1.2 в WebAssembly и выполняется в отдельном Web Worker.

## Быстрый старт

Нужен Node.js 22.13+ и npm. Из корня репозитория перейдите в папку сайта:

```bash
cd site
npm ci
npm run toolchain
npm run dev
```

Откройте адрес, выведенный Vite (обычно `http://127.0.0.1:5173`). При первой подготовке скачивается около 71 МБ toolchain. В дальнейшем проверенные бинарные файлы используются повторно. `npm run toolchain` требует доступ к raw.githubusercontent.com для артефактов и лицензий.

```bash
npm test
npm run build
npm run preview
```

Сборка находится в `dist/`. Если пропустить `npm run toolchain`, материалы будут доступны, но при запуске C появится ошибка загрузки компилятора. Скрипт сборки намеренно не скачивает файлы из сети: подготовка toolchain — отдельный явный шаг.

Для проверки публикации в подкаталоге:

```bash
npm run build -- --base=/hse-se-prog-seminars/
npm run preview -- --base=/hse-se-prog-seminars/
```

В PowerShell используйте `$env:BASE_PATH='/hse-se-prog-seminars/'; npm run build; npm run preview`: некоторые версии npm.ps1 не передают дополнительные CLI-флаги после `--`. Для тестов подкаталога предусмотрена переносимая команда `npm run build:qa`. HashRouter сохраняет прямые ссылки вида `/hse-se-prog-seminars/#/notes/seminar-01/topics/01-introduction` при обновлении страницы. Удалите переменную BASE_PATH для обычного запуска из корня.

## GitHub Pages

1. Проверьте `repository` в `site.config.json`: сейчас `monkeybonbon/hse-se-prog-seminars`. При переносе проекта измените его, чтобы ссылки на Git и инструкции указывали на ваш репозиторий.
2. Отправьте исходники в `main`.
3. В **Settings → Pages → Build and deployment → Source** выберите **GitHub Actions**.
4. Разрешите GitHub Actions в настройках репозитория. Проверьте, что среда `github-pages` разрешает deployment из `main`, и защитите `main` от записи студентов.
5. Запустите **Actions → Publish notes and submissions → Run workflow** или дождитесь push в `main`.

Workflow `../.github/workflows/pages.yml` устанавливает зависимости, подготавливает toolchain, обнаруживает конспекты, читает студенческие ветки через REST API, выполняет тесты, собирает сайт и публикует artifact. Команды выполняются в `site/`, пути кешей и artifact заданы от корня репозитория. Базовый путь определяется из имени репозитория; для `*.github.io` используется `/`. Параллельные публикации сериализованы через concurrency.

Workflow запускается при push в `main`, вручную и каждые 15 минут. GitHub может задерживать или пропускать scheduled runs; в неактивных публичных репозиториях расписание может отключаться. Push в ветку студента сам по себе не запускает публикацию из `main`. Для немедленного обновления преподаватель запускает workflow вручную.

`GITHUB_TOKEN` доступен **только шагу collect** в CI. Разрешения: `contents: read` для сборки; `pages: write` и `id-token: write` только для deployment job. Не создавайте `VITE_GITHUB_TOKEN`, не помещайте токен в конфигурацию сайта. При локальной сборке отчёт изначально честно помечен недоступным.

## Структура

```text
.github/workflows/             # автоматическая сборка и публикация
.gitignore
README.md                      # короткая инструкция студентам
submissions/                   # решения студентов в их ветках
  README.md
site/                          # весь сайт и документация преподавателя
  README.md
  notes/                       # единственный источник учебного контента
    seminar-01/
      topics/*.md              # темы
      tasks.md                 # задания и их количество
      assets/                  # вложения
  src/                         # React / TypeScript / CSS
  scripts/                     # генерация контента, сбор сдач, подготовка toolchain
  public/c-worker.mjs           # compiler pipeline и WASI host
  public/submissions.json       # опубликованный отчёт (генерируется collect)
  tests/                       # unit/integration и browser tests
  site.config.json             # URL репозитория, regex веток, лимиты
  package.json
  package-lock.json
```

Далее пути к конспектам, настройкам и файлам приложения указаны **относительно `site/`**. Все npm-команды выполняйте из `site/`. Git-команды сдачи выполняются **из корня репозитория**, где остаётся `submissions/`; менять формат студенческих веток и пути решений не требуется.

`site/src/generated/`, `site/public/content/`, `site/public/toolchain/`, `site/dist/` игнорируются Git и создаются автоматически. Не редактируйте сгенерированный контент. Корневая `submissions/` никогда не импортируется в конспекты и не копируется в сборку.

## Добавление семинара и темы

Создайте, например, `notes/seminar-04/topics/01-функции.md`:

````markdown
# Функции

Текст с обычным Markdown.

```c id=first-function
#include <stdio.h>
int square(int n) { return n * n; }
int main(void) { printf("%d\n", square(7)); return 0; }
```
````

Новая папка `seminar-04` автоматически создаёт семинар. Любой `.md` в `topics/` (включая вложенные папки) становится темой. Темы сортируются по числовым префиксам и алфавиту; заголовок берётся из первого H1, иначе — из имени файла без префикса. После удаления, переименования и изменения файлов сайт перестраивается без ручных импортов. Исходные `.md` при сборке не изменяются. В dev-режиме изменения `notes/` отслеживает Vite.

## Markdown и Obsidian

Поддерживаются заголовки, списки, таблицы GFM, цитаты, ссылки, картинки, fenced code blocks и формулы `$x^2$` / `$$...$$` (KaTeX).

```markdown
[[Название заметки]]
[[Название заметки|Подпись]]
[[Название заметки#Раздел]]
[[seminar-02/topics/02-loops|Циклы]]
![[схема с пробелом.png]]
![Подпись](../assets/схема.png)
[Следующая тема](02-data-types.md)
[Внутренний раздел](#имя-раздела)

> [!NOTE]
> Подсказка.
```

Вложение кладите в `notes/seminar-XX/assets/`. Поддерживаются русские имена, Unicode и пробелы. Для wikilinks можно использовать имя файла без `.md` или точный H1. Сначала проверяется путь относительно текущей заметки и от `notes/`, затем уникальное имя файла или заголовок. Если есть совпадающие имена, укажите полный путь. Неоднозначные и неразрешённые внутренние ссылки выводятся как предупреждения `[content]` при сборке.

Обычные ссылки на Markdown должны содержать `.md`; ссылки на изображения и вложения разрешаются относительно заметки. Заголовки получают GitHub-подобные slug, повторяющимся добавляются суффиксы `-1`, `-2`. Трансклюзия других заметок, Obsidian block references `^id`, Dataview и Mermaid не реализованы. Callout NOTE/TIP/WARNING/IMPORTANT поддерживаются как стилизованные цитаты. Произвольный HTML не исполняется; JavaScript URL фильтруются react-markdown, HTML-плагины не включены.

## Интерактивные примеры

Каждый fenced-блок `c` становится отдельным редактором. У других языков обычная подсветка и копирование. Используйте полный файл C с `main`, иначе компилятор или линкер сообщит об ошибке. Для stdin раскройте «Ввод программы» и введите все данные перед запуском.

Явный `id` в metadata блока рекомендуется для стабильного сохранения:

````markdown
```c id=sum-example
/* программа */
```
````

В одной заметке ID должны быть уникальны. Также поддерживается `c #sum-example`. Без ID используется позиционный `block-0`, `block-1` среди блоков C. Ключ localStorage: `c-notes:v1:<путь заметки>:<ID>`. Перестановка размеченных блоков не теряет правки. Перемещение самой заметки меняет ключ; для восстановления старые данные остаются в localStorage под прежним путём.

Правки сохраняются при вводе и восстанавливаются после навигации и перезагрузки. Обновление исходного конспекта их не стирает. «Сбросить» заменяет правки актуальным исходником Markdown. Хранилище локально для origin браузера, не синхронизируется и не отправляется в Git. При запрете localStorage или переполнении показывается предупреждение.

Кнопка «Запустить» и Ctrl/⌘ + Enter запускают Clang `-std=c11 -Wall -Wextra -O0`, затем wasm-ld и WASI-программу. Есть независимые вкладки stdout, stderr, сообщений компилятора и код завершения. Компилятор загружается только при первом запуске; HTTP-кеш браузера позволяет использовать загруженные файлы повторно. Worker завершается после каждого запуска, ошибки, остановки и ухода со страницы.

Ограничения: 10 секунд **выполнения программы**, 120 секунд на загрузку и компиляцию; линейная память программы до 64 МиБ; вывод до 1 МиБ. Компилятор требует дополнительно несколько сотен МБ памяти браузера. Значения времени настраиваются в `site.config.json`. На слабых телефонах первая компиляция может быть медленной. Это C11 / wasm32, без C++, процессов, потоков, сокетов, доступа к файловой системе компьютера и интерактивного терминала. `stdio.h`, `stdlib.h`, `string.h`, `math.h`, `printf`, `scanf`, malloc/free проверены. Не все системные вызовы WASI реализованы: неподдерживаемые возвращают NOSYS; работа с файлами недоступна. Проверка границ массивов и sanitizers не включены.

Используются однопоточные WASM-модули; SharedArrayBuffer, COOP/COEP и серверные заголовки изоляции не требуются. Это позволяет публиковать сайт на обычном GitHub Pages. Бинарные файлы, sysroot и лицензии публикуются в том же origin, пользовательский код никуда не отправляется.

## Задания и количество столбцов

Создайте `notes/seminar-04/tasks.md`:

```markdown
---
taskCount: 2
---
# Задания на семинар 4

## 1. Первая задача
Условие. Файл 1.c.

## 2. Вторая задача
Условие. Файл 2.c.
```

Файл появляется во вкладке «Задания на семинар». Ниже автоматически добавляется инструкция Git с URL из `site.config.json`. `taskCount` — явное число заданий, а не максимальный номер студенческого файла. При отсутствии метаданных выводится предупреждение, столбцов задач не будет. У каждого семинара может быть своё количество заданий.

## Доступ студентов и сдача через Git

Преподаватель приглашает студентов в collaborators репозитория с правом создания веток либо выдаёт доступ через GitHub organization/team. Защитите `main` ruleset/branch protection: требуйте review ответственного преподавателя, запретите force push и удаление, ограничьте обход правил. Ветка студента и изменения workflow в ней не участвуют в публикации основной версии. В публичном репозитории код и опубликованная таблица видны всем; в приватном доступность Pages зависит от настроек и тарифа GitHub.

Формат ветки строго `BPI<номер группы>_<Фамилия латиницей без пробелов>`, например `BPI2412_Ivanov`; regex задаётся в `site.config.json`. При изменении regex сохраняйте смысл `группа_фамилия`: эти поля извлекаются по подчёркиванию.

```bash
git clone https://github.com/monkeybonbon/hse-se-prog-seminars.git
cd hse-se-prog-seminars
git switch -c BPI2412_Ivanov
mkdir -p submissions/seminar-01
# Создайте 1.c, 2.c, 3.c — самостоятельные решения
git add submissions/seminar-01/
git commit -m "Submit seminar 01 tasks"
git push -u origin BPI2412_Ivanov
```

В Windows используйте Git Bash. Если нет права записи, обратитесь к преподавателю. Студент отправляет свою ветку, не `main`. PR и merge не нужны. Следующие семинары добавляются в той же ветке: `submissions/seminar-02/1.c` и т. д.

## Сбор и просмотр сдач

`npm run content` генерирует конфигурацию семинаров; `npm run collect` создаёт `public/submissions.json`. Локально для публичного репозитория возможен запуск без токена, с более низким лимитом GitHub API. Скрипт при необходимости читает `GITHUB_TOKEN` из окружения, но не публикует его. На GitHub используется автоматически выданный token только внутри Actions.

Сборщик:

- читает все страницы `/branches`, проверяет имена по regex;
- фиксирует commit SHA и читает дерево по нему, не содержимое файлов;
- при `truncated` делает полный обход только `submissions/` и каталогов семинаров;
- распознаёт только обычные файлы `submissions/seminar-XX/N.c` с ожидаемым номером, игнорирует symlinks;
- предупреждает о неизвестных путях/номерах и неверных именах веток;
- делает ограниченные повторные попытки при сетевых ошибках, 5xx и rate limits;
- при недоступности отдельной ветки помечает её как «Нет данных», а не «Не загружено»;
- при общей ошибке сохраняет предыдущий отчёт (если доступен), помечает его недоступным и сохраняет время неудачной попытки.

CI кеширует предыдущий отчёт для восстановления при ошибке API. Ссылки в таблице закреплены за commit SHA, поэтому соответствуют собранному состоянию. Дата последнего commit относится ко всей ветке, а не к отдельному решению. Наличие даже пустого `.c` означает только факт загрузки: содержимое намеренно не читается и не проверяется. Статусы: **«Загружено»**, **«Не загружено»**, **«Нет данных»** при ошибке сбора. Есть фильтры по группе, семинару и фамилии, горизонтальная прокрутка на телефонах и время обновления. Через 45 минут отчёт помечается устаревшим. «Обновить данные» перечитывает опубликованный JSON, а не запускает Actions.

Необязательный `site/students.json` (рядом с `site.config.json`) позволяет показать студентов без ветки:

```json
[
  "BPI2412_Ivanov",
  "BPI2412_Petrov",
  { "branch": "BPI2413_Sidorov" }
]
```

Без файла показываются только найденные корректные ветки. Не храните здесь лишние персональные данные. Чтение веток требует запросов на каждого студента; лимиты API и время Actions ограничивают масштаб. Деревья студенческих веток не checkout-ятся, C-файлы не выполняются, их workflow не используется для deployment.

## Проверки

```bash
npm test
npm run toolchain
npm run build:qa
npx playwright install chromium
npm run test:e2e
```

Если Chrome уже установлен, PowerShell: `$env:PLAYWRIGHT_CHANNEL='chrome'; npm run test:e2e`. В CI используйте `npx playwright install --with-deps chromium`. E2E поднимает собственный сервер готовой сборки на `127.0.0.1:4173/qa-repo/`, использует непустой base path и запускает настоящий WASM toolchain. Не запускайте другие серверы на этом порту.

Unit/integration тесты проверяют обнаружение/удаление тем и assets, неизменность исходников, сортировку, Unicode, Obsidian-ссылки, якоря, стабильные ID, пагинацию, roster, неизвестные файлы, truncated trees, удалённые ветки и rate limits на фиктивных API-ответах. Для этих тестов реальные ветки и доступ к сети не нужны.

E2E проверяют фактическую компиляцию изменённого C, `scanf`, stdout/stderr, exit code, ошибки и их исправление, stdlib/string/math, указатели и циклы, восстановление и сброс редакторов, независимые состояния, timeout/остановку, отказ загрузки toolchain, фильтры отчёта, мобильную навигацию, картинки, формулы, прямые ссылки и обновление страницы. Скриншоты desktop/mobile сохраняются в `.local/`; при ошибках Playwright — в `test-results/`.

Ручная проверка перед занятием: откройте реальный Pages URL, запустите printf и scanf, проверьте мобильное меню, добавьте временную заметку через `main` и убедитесь, что Actions её публикует. После первого реального push ветки студента дождитесь расписания и сравните ссылки/статусы с деревом GitHub. Эти внешние проверки требуют настроенного GitHub Pages и не заменяются локальным успешным build.

## Дизайн и лицензии

Пастельно-розовая рабочая область, сиреневые панели, бордовые заголовки, компактные элементы, самостоятельный леопардовый SVG-узор. Скриншот Obsidian в предоставленном вложении отсутствовал; оформление выполнено по текстовому описанию. Картинка интерфейса не используется как фон. Основной шрифт имеет системный fallback, моноширинный — системный.

Лицензии toolchain, происхождение закреплённых бинарных файлов и объяснение выбора интеграции: [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md). Исходное приложение Derle не скопировано. Артефакты готовятся скриптом с проверкой Git blob SHA-1; изменение toolchain требует обновить ревизию, хеши и версию ключа CI-кеша.
